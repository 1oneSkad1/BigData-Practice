# Task 2 · 이 PC에서 측정한 스트림 메모리 한계

## 측정 환경과 재현

- 측정일: 2026-10-07, Asia/Seoul. CPU: Intel(R) Core(TM) Ultra 5 228V.
- OS: Windows-11-10.0.26200-SP0; Python: 3.14.3.
- Windows에서 확인한 사용 가능한 총 RAM: 31.51GiB, 측정 시작 전 여유 RAM: 14.49GiB.
- 실행 중이던 프로그램: ChatGPT/Codex, Chrome, Explorer, Windows Defender(MsMpEng), Memory Compression, WorkloadsSessionHost 등. 샘플별 working set은 `machine_context.json`에 보존했습니다. 프로그램의 working set을 합산해 RAM을 추정하지 않았습니다.
- 이 컴퓨터의 Codex 실행 환경에서 실제 실행했습니다. `tracemalloc`으로 각 방법을 따로 측정한 Python 할당 피크입니다. 전체 프로세스 RSS나 다른 프로그램의 메모리가 아니며, `tracemalloc` 비용이 wall time에 포함됩니다.
- 고정 시드 246, distinct 후보 범위 `int(0.4*n)`의 난수 스트림을 generator로 한 번씩 읽었습니다. exact와 FM에는 같은 스트림을 각각 재생했고, FM 오차의 분모는 기대 distinct 수가 아니라 exact의 실측 distinct 수입니다.

```bash
python task2_limits.py --sizes 100000,400000,1600000,6400000
python task2_limits.py --sizes 25000000
```

## A2 · 어디에서 멈췄는가

2,500만 항목에서 exact의 44.28초 대기는 대화형 처리의 실용적 기준인 방법별 30초를 넘었습니다. 그래서 여기에서 실험을 멈췄습니다. 마지막으로 30초 안에 끝난 크기는 640만 항목(9.86초)입니다. 측정한 크기 사이에서는 640만~2,500만 구간에서 이 시간 기준을 넘었으며, 더 촘촘한 측정 없이 정확한 임계 n을 단정할 수 없습니다.

먼저 부담스러워진 자원은 **시간**입니다. 2,500만 항목도 끝까지 성공했고 약 744.7MB의 Python 피크만 사용했으므로, 이 PC의 RAM 고갈 지점이나 exact 계산이 절대 불가능해지는 크기를 찾았다고 주장하지 않습니다. FM도 184.30초가 걸려 시간 문제의 해결책은 아니었습니다.

## A4 · 두 성장률

n은 250배 증가했고 exact 피크는 189.72배 증가했습니다. 끝점의 경험적 지수 `ln(M_last/M_first)/ln(n_last/n_first)`는 0.950이며, 증가분 기울기는 입력 항목당 약 29.75bytes입니다. distinct 비율이 거의 일정한 이 실험에서는 **O(n)**으로 해석합니다. set의 테이블 확장과 Python 문자열 오버헤드 때문에 정확히 직선이거나 동일한 항목당 상수가 되지는 않습니다.

FM 피크는 4,021~4,200bytes, 끝점 비율 0.976배, 경험적 지수 -0.004입니다. 이는 **O(1)**에 해당하는 거의 평평한 곡선입니다. 기본 64개의 최대 trailing-zero 레지스터와 8개 결합 그룹, 현재 항목의 해시만 보존하며 스트림은 저장하지 않습니다. 실제 키 문자열 길이와 임시 할당에 따른 수백 bytes 차이는 데이터 저장량의 선형 증가가 아닙니다.

## A5 · 정확도는 좋아졌는가

비율은 0.943x, 0.587x, 0.698x, 1.089x, 1.007x로 변했습니다. 이번 다섯 크기는 모두 0.5~2배 안에 들어왔지만, n에 따라 단조롭게 개선되거나 악화되지 않았습니다. 레지스터 수를 고정했기 때문에 해시 최대값의 확률적 변동은 남습니다. FM은 stochastic averaging 변형이며, 선택한 기하평균/중앙값 결합과 고정 감쇠는 정확한 값이나 불편 추정을 보장하지 않습니다.

## 비용과 판단

Exact는 9,179,304개의 서로 다른 문자열을 저장해 정확한 값을 제공합니다. FM은 약 4KB만 유지하지만 마지막 크기에서도 1.007배의 근삿값이며, 이 Python 구현은 exact보다 느립니다. 메모리 제약 하의 대략적인 규모 파악에는 유용하고 정확한 방문자 과금이나 작은 변화 감지에는 부족합니다. RAM이 충분한 현재 크기에서 exact를 포기해야 한다고 결론내리지 않았습니다.
